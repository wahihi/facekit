## 남은 일

1. **나머지 방향 미검증** — `landscapeLeft`. 아직 실기기 테스트 없음.
   오버레이 박스가 실제 얼굴과 정확히 겹치는지(육안)도 확인 안 됨.
   `[_cameraQuarterTurns]` 디버그 로그의 `turns` 값이 방향별로 기대한
   대로 바뀌는지도 같이 확인.

   `portraitDown`은 2026-08-16 `log7.txt`로 시도했으나 안드로이드
   방향 센서 자체가 그 상태를 한 번도 안 잡아줘서(폰을 물리적으로
   뒤집어도 `[_cameraQuarterTurns]`엔 `portraitUp`/`landscapeRight`만
   찍힘 — 안드로이드가 기본적으로 "거꾸로 세로" 자동회전을 막아두는
   경우가 흔함) 실질적으로 테스트가 안 됐고, 사용자 판단으로 **의도적
   보류**(실사용에서 폰을 거꾸로 세로로 들 일이 거의 없어 검증 가치
   낮음으로 결정, 2026-08-16).

2. **`_framingHint` 실사용 확인** — 줌이 최대인데도 얼굴이 작을 때 뜨는
   안내 문구("카메라에 조금 더 가까이 와주세요")가 실제로 뜬 사례가
   아직 로그에 없음. 최대 줌으로도 부족할 만큼 멀리 있어보는 테스트 필요.

3. **라이브니스 — GitHub Issue #4로 분리, 장기 검토. 데모 때는 계속
   꺼둠(2026-08-16 확정)**
   (https://github.com/wahihi/facekit/issues/4). 2026-08-16 `log9.txt`로
   `true`로 되돌려서 통합 테스트해봤는데, 두 가지 문제가 나와서 다시
   `false`로 되돌림:
   - **성능**: `MediaPipeFaceLandmarker.detectLandmarks`가 매 프레임
     다시 돌면서 `onFrame` 처리 시간이 중앙값 55ms→186ms로 3~5배 느려짐
     → 깜빡임을 못 잡고 `face lost` 리셋이 훨씬 잦아짐("여러 번
     깜빡였는데 통과 못 함" 체감 문제)
   - **보안**: `LivenessState.passed`가 매 `identify()` 시도마다
     재검증되는 게 아니라 추적이 안 끊기는 한 계속 유지됨 — 모니터로
     타인 사진을 비췄더니 라이브니스 게이트를 그냥 통과함(매칭
     단계에서만 걸러짐). 등록된 본인 사진이었다면 깜빡임 없이 통과됐을
     구조적 취약점.
   - 이슈에 두 문제 다 정리해두고 원인·대응 후보까지 남겨둠. 데모는
     라이브니스 없이 진행하기로 결정.

4. **세로로 긴 프레임에서 가운데 크롭 수직 중심 미세조정 — GitHub
   Issue #3로 분리, 추후 디버깅 예정**
   (https://github.com/wahihi/facekit/issues/3). `log8.txt`(2026-08-16)로
   재확인해보니 이전 평가(32.7%, "급하지 않음")보다 실제로 더 심각했다 —
   같은 세션에서 portraitUp 92.3% accepted인데 landscapeLeft/Right는
   59~70%대로 떨어짐, 가운데 크롭 적중률도 9~26%까지 낮게 나온 구간
   있음. 다만 **데모는 세로로 진행할 예정**이라 지금 당장 막는 문제는
   아님 — 위 이슈에 실측 데이터·가설·다음에 확인할 것(CameraPreview
   letterbox 여부 등) 정리해둠, 여유 있을 때 착수.

5. **(미해결, 참고용) 리파인먼트 fallback의 정확한 메커니즘은 직접 증명
   안 됨** — "부정확한 1차 bbox → 크롭이 실제로 얼굴을 빗나감"이라는
   가설은 결과 개선으로 간접 확인됐을 뿐, 크롭 좌표 vs 실제 얼굴 위치를
   직접 비교해서 증명한 적은 없음. 로그에 크롭 영역/1차 bbox는 이미
   남기고 있으니, 다음에 fallback이 다시 발생하면 좌표 비교 가능.
