# 정렬 행렬이 틀렸던 하루 — 버그 네 개가 층층이 쌓여있었던 이야기

**날짜:** 2026-08-03
**계기:** 증상 재현이 아니라 **코드 리뷰**에서 시작됐다. 공개 저장소를 다시 읽으며
`AffineAligner`의 Umeyama/SVD 구현을 Umeyama(1991) 논문과 대조하다가, 코드를
실행조차 안 해보고 수상한 지점 두 개를 짚어냈다. 여기서 시작해서 실기기까지
왕복하며 파다 보니 **서로 완전히 다른 층위의 버그가 넷** 나왔다.
**결론(스포일러):** (1) SVD 부호 버그, (2) 공분산 정규화 누락, (3) 전면 카메라
회전 공식 버그, (4) BlazeFace 랜드마크 대응관계 버그(눈 좌우 순서 + 억지 5번째
점). 넷 다 서로 다른 원인이고, 하나를 고칠 때마다 "나아졌는데 여전히 이상하다"가
반복됐다. 최종적으로 정렬된 크롭이 실제로 똑바로 선 얼굴로 나오는 것을 육안으로
확인했고, 실기기 재측정에서 동일인 유사도 46회 전부 accepted(0.776~0.979,
평균 0.906)로 정상화됐다.

이 프로젝트는 [Claude Code](https://github.com/anthropics/claude-code)와
협업해서 개발했고, 이 디버깅도 마찬가지다. 틀린 가설과 예측이 빗나간 지점까지
그대로 남겨둔다.

## 0. 배경 — 코드 리뷰에서 출발했다

이전 세션들은 매니페스트, 정규화 상수, 라이선스, ONNX↔TFLite 변환, 벤치마크,
보고서 문구를 다뤘다. `affine_aligner.dart`를 연 적은 없었다. 이번 세션은
"GitHub에 실제 코드가 있는데 확인해서 설명해줄 수 있냐"는 요청으로 시작됐고,
저장소를 클론해서 `AffineAligner`의 5점 유사변환(similarity transform) 구현을
논문 III절의 검증 가능한 수치 예제와 대조하는 작업으로 이어졌다.

이 단계에서 **실행 없이 코드만 읽고** 두 가지 후보를 짚었다:

- `_svd2x2`의 `vt` 부호 — 주석은 `rot(-theta) transposed = rot(theta)`라고 맞게
  적혀 있는데, 코드는 `rot(-θ)`를 그대로 쓰고 있었다.
- `_umeyamaSimilarity`의 `srcVar /= n;`은 있는데 공분산 4개 항(`cov00`~`cov11`)에는
  `/n`이 빠져 있었다.

같은 검토에서 "6개 사전 확인 과제" 형태의 예측 목록도 나왔었다(인자 순서,
Σxy와 R=USVᵀ 짝, det(U)·det(V) 반사 가드 통합 제안, 특이값 정렬, 단위 테스트
부재 등). 나중에 실제 코드와 대조한 결과 **6개 중 2개만 적중**했고(1/n 누락,
테스트 부재), det(U)·det(V) 통합 제안은 이 구현엔 적용이 안 됐으며(아래 1절
참고), **가장 심각했던 버그(vt 부호)는 애초에 그 예측 목록에 없었다.** 이론적
사전 분석이 실행 결과를 대체할 수 없다는 걸 이 프로젝트에서 다시 한번 보여준
사례다.

## 1. 정적 분석 검증 — Python 재구현으로 대조

코드 리뷰 결과를 그대로 믿지 않고, `_svd2x2`/`_umeyamaSimilarity`를 Python으로
라인 대 라인 포팅해서 numpy 표준 SVD 기반의 독립 Umeyama 구현과 대조했다.

**vt 부호 버그 확인** — 무작위 2×2 행렬 5개로 `U·diag(s)·Vᵀ`를 재구성했더니
현재 코드는 전부 원본을 복원 못 했고(`atol=1e-8` 기준 전부 실패), 부호를
`[vCos, -vSin, vSin, vCos]`로 고치면 전부 복원됐다.

**공분산 `/n` 누락 확인** — `arcface112Ref`를 자기 자신에 맞추는 항등 케이스에서
현재 코드의 스케일이 `sigma=5.0`으로 나왔는데, 이건 점 개수 `n=5`와 정확히
일치했다(분자는 정규화 안 됨, 분모만 정규화되어 n배 부풀려짐).

**논문 예제 재현** — 두 버그를 모두 고친 버전으로 Umeyama(1991) III절의 3점
예제(`src=[(0,0),(1,0),(0,2)]`, `dst=[(0,0),(-1,0),(0,2)]`)를 돌리니
`c=0.72111`, `R=[[0.6,0.4],[-0.4,0.6]]`, `t=(-0.8,0.4)` — 논문 발표값과
정확히 일치했다. numpy 표준 SVD 기반 독립 구현과도 소수점까지 일치했다.

**반사(reflection) 가드는 죽은 코드였지만 결과적으로 옳았다** — `_svd2x2`가
구성하는 `U`, `Vt`는 항상 순수 회전(det=+1)이라 `detU·detVt`는 이 구현에서
절대 음수가 될 수 없다. 즉 반사 가드 분기(`sign`)는 한 번도 실행되지 않는
죽은 코드다. 그런데도 미러링된 입력(좌우 반전)을 넣어 확인하니 결과 `R`이
`det=1`(반사 아님)로 정확히 처리됐다 — 이 해석적 SVD 공식은 특이값 `s1`이
음수로 나올 수 있고, 그 부호 안에 반사 정보가 이미 녹아 있기 때문이다.
일반적인 SVD 라이브러리를 쓸 때와 규약이 달라서, 이전 세션의 "det(U)·det(V)로
통합하라"는 조언은 이 구현엔 적용되지 않는다는 게 확인됐다.

**기존 테스트가 이 버그들을 구조적으로 못 잡는 이유** — 기존
`test/alignment/affine_aligner_test.dart`의 "identity transform" 테스트는
단색(solid colour) 이미지를 썼는데, 단색 이미지는 어떤 아핀 변환(5배 확대든
180° 뒤집기든)을 거쳐도 똑같은 단색으로 남는다. 테스트 이름은 "identity"인데
정작 변환이 항등인지는 한 번도 검사하지 않았다. 게다가 그 테스트가 쓰는
`_identityFace()`는 `arcface112Ref`(5점)를 랜드마크로 넘기는데, `_pickFivePoints`가
`lm.length<6`일 때 5번째 점을 `lm[3]`으로 복제해버려서 `src=[p0,p1,p2,p3,p3]`가
되어 애초에 진짜 항등 케이스가 아니었다.

## 2. 실기기 확정 — 진단용 테스트 추가

이론 검증만으로는 부족해서, `AffineAligner`에 `@visibleForTesting` 훅
(`umeyamaSimilarityForTest`)을 뚫어 private 함수를 테스트에서 직접 부를 수
있게 하고, 다음 진단 테스트를 추가했다:

```dart
test('DIAG: ref → ref must be identity', () {
  final m = umeyamaSimilarityForTest(arcface112Ref, arcface112Ref);
  expect(m[0], closeTo(1, 1e-6));
  expect(m[4], closeTo(1, 1e-6));
});
```

`flutter test`로 돌린 실제 결과(수정 전):

```
a=-4.9996839220786224 b=-0.056219919143706894 tx=340.1815074057739
c=0.056219919143706894 d=-4.9996839220786224 ty=428.2321675657798
```

Python 포팅으로 예측한 값과 소수점까지 일치했다 — `-5`의 크기는 점 개수
`n=5`(공분산 `/n` 누락), 음수 부호는 `vt` 부호 뒤집힘이었다. 두 줄을 고친 뒤
같은 테스트를 다시 돌리니:

```
a=0.9999999999999999 b=0.0 tx=7.105427357601002e-15
c=0.0 d=0.9999999999999999 ty=1.4210854715202004e-14
```

부동소수 잡음 수준의 항등행렬. 전체 테스트 스위트(80개)도 회귀 없이 통과했다.

**수정:**
```dart
// _svd2x2
- final vt = [vCos, vSin, -vSin, vCos];
+ final vt = [vCos, -vSin, vSin, vCos];

// _umeyamaSimilarity
  srcVar /= n;
+ cov00 /= n; cov01 /= n; cov10 /= n; cov11 /= n;
```

`detU/detVt/sign/scaledS` 죽은 코드는 이번엔 건드리지 않았다(1절 참고 — 이
구현에선 항상 무해하게 우회되므로, 굳이 지금 손대서 검증 범위를 늘릴
이유가 없었다).

## 3. 실기기에서 재현 — 두 수학 버그는 고쳤는데 크롭이 여전히 이상하다

`flutter run --dart-define=FACEKIT_VERBOSE_DEBUG=true`로 Pixel 7 실기기에서
enroll을 실행하고 `[AffineAligner] DEBUG MATRIX`와 base64로 쪼개서 찍은 크롭
덤프를 로그로 받았다. 로그의 행렬 값을 numpy 표준 Umeyama 구현으로 독립
재계산해서 대조하니 **소수점까지 정확히 일치** — 수정된 코드가 기기에서
정상 실행되고 있다는 게 확정됐다. 문제는 그 다음이었다.

크롭을 base64 청크에서 PNG로 복원해서 보니, 얼굴이 대각선으로 기울어진 채
프레임 아래쪽에 걸쳐 있었고 옆으로 창틀/블라인드 같은 배경이 크게 들어와
있었다. 행렬에서 회전각을 뽑아보니 6개 검출 전부 116°~173° 범위였고 부호도
한 번 뒤집혔다. 스케일은 `sigma≈0.05~0.12` — 검출된 5점 간격이 참조
레이아웃보다 8~20배 크다고 판단한 것이었다.

**흔들림(모션 블러) 가설을 배제했다.** 종화님이 "너무 빨리 흔들어서 그런 거
아니냐"고 물었는데, 데이터가 그 가설과 안 맞았다. 6개 프레임 전부에서 "눈"으로
추정되는 두 점(인덱스 0,1)이 가로(dx)로는 0.6~16px밖에 안 벌어지고 세로(dy)로는
항상 107~140px 벌어져 있었다. 흔들림이라면 프레임마다 무작위 패턴이어야 하는데,
6번 다 "가로는 좁고 세로는 넓다"는 동일 패턴이 나온 건 코드 쪽 문제라는 신호였다.

## 4. 카메라 회전 공식 버그

**"기기를 눕혔나?" 가설도 배제했다.** 종화님이 "세로로 셀카 찍듯 계속 들고
있었고, 가로로 테스트한 적은 한 번도 없다"고 확인해줬다. 그리고 7/24
포스트모템에서 이미 카메라 회전 버그를 고친 이력이 있는데, git 이력을 보니
`image_converter.dart`/`main.dart`의 회전 관련 코드는 그 수정(`aa525e6`)
이후 **한 번도 안 바뀌었다.** 그날도 지금과 같은 전면 카메라 기본값 조건에서
"크롭이 똑바로 선 얼굴로 나오는 걸 확인했다"고 문서에 남아 있었다. 같은 코드가
같은 조건에서 그때는 맞았는데 지금은 틀려 보인다 — 이건 회귀가 아니라 놓친
엣지케이스일 가능성이 높았다.

`_cameraQuarterTurns()`에 임시 디버그 print를 추가해서 실측했다:

```
lensDirection=CameraLensDirection.front sensorOrientation=270 degrees=90 turns=1
```

`rotateFaceImage()`의 회전 로직 자체는 numpy `rot90(k=-1)`(90° 시계방향)과
정확히 일치해서 무죄였다. 문제는 몇 도를 돌릴지 계산하는 공식 쪽이었다.

**턴 값을 실측으로 역산했다.** `turns=1`로 나온 실제 출력 랜드마크 좌표를
`rotateFaceImage`의 역변환으로 회전 전(raw, 720×480 랜드스케이프) 좌표로
복원한 뒤, 4가지 후보(`turns=0,1,2,3`)를 각각 정방향으로 적용해서 어느 게
정상적인 얼굴 기하를 만드는지 비교했다:

```
turns=0: dx=105.6 dy=9.6   (가로 정상)  ← 그런데 코가 눈 위, 입이 코 위 (거꾸로)
turns=1: dx=9.6  dy=105.6  (세로 비정상, 현재 코드)
turns=2: dx=105.6 dy=9.6   (가로 정상)  ← 코가 눈 아래, 입이 코 아래 (정상)
turns=3: dx=9.6  dy=105.6  (세로 비정상)
```

`turns=2`만 눈이 가로로 벌어지고 위/아래 순서(코<눈, 입<코)까지 맞았다.
전면 카메라 공식을 다음과 같이 고쳤다:

```dart
// example/lib/main.dart, _cameraQuarterTurns()
- (360 - sensorOrientation) % 360
+ (450 - sensorOrientation) % 360
```

`sensorOrientation=270`일 때 `degrees=90(turns=1)` → `degrees=180(turns=2)`로
바뀐다. 이 값은 카메라 이론을 다시 유도한 게 아니라 **이 기기·이 렌즈에서
실측으로 검증된 값**이다(주석에 명시). 흔히 쓰이는 ML Kit 스타일 공식대로라면
`turns=3`이 나와야 하는데, 이 실측 데이터로는 `turns=2`가 맞았다 — Flutter
`camera` 플러그인이나 이 기기의 펌웨어가 표준 Camera2 `SENSOR_ORIENTATION`
특성과 다르게 동작할 가능성이 있지만, 정확한 이유는 규명하지 않았다.
**후면 카메라 분기는 건드리지 않았고 검증도 안 됐다** — 종화님이 후면 카메라를
아예 안 쓰기 때문에 확인할 방법이 없었다(추후 과제로 남김, 6절 참고).

재확인 결과 9개 프레임 전부 눈이 가로로(dx=87~126px, dy=9~24px) 벌어졌다.
카메라 회전 문제는 해결됐다 — 그런데 여전히 정렬 행렬의 회전각이
42°~90°로 남아 있었다.

## 5. 랜드마크 대응관계 버그 — 눈 좌우 순서 + 억지 5번째 점

`_pickFivePoints`는 BlazeFace의 6개 키포인트 중 처음 4개(눈,눈,코,입)를 그대로
쓰고 5번째는 귀 중점을 만들어 썼다:

```dart
static List<Point> _pickFivePoints(List<Point> lm) {
  final fifth = lm.length >= 6
      ? Point((lm[4].x + lm[5].x) / 2, (lm[4].y + lm[5].y) / 2)
      : lm[3];
  return [lm[0], lm[1], lm[2], lm[3], fifth];
}
```

두 가지가 겹쳐 있었다.

**(1) 눈 좌우 인덱스가 반대였다.** `blazeface_decoder.dart:21` 주석은
"Keypoint order: rightEye, leftEye, nose, mouth, rightEar, leftEar"라고
적혀 있는데, `affine_aligner.dart:63-64` 주석은 "leftEye[0], rightEye[1]"이라고
반대로 적혀 있었다. 실제 검출된 랜드마크로 검증했다: 실기기에서 나온 9개
프레임의 눈+코+입 4점을 4점 참조(눈2+코+입중앙)에 맞춰봤더니, **눈 인덱스를
그대로 쓰면 회전 42°~90°에 스케일이 0.07~0.13으로 들쭉날쭉**했고, **인덱스
0,1을 스왑하면 회전이 13°~24°(자연스러운 고개 기울임 범위)로, 스케일도
0.30~0.42로 안정적으로** 바뀌었다. `blazeface_decoder.dart`의 순서가 맞고
`affine_aligner.dart`의 가정이 틀렸다는 게 확정됐다.

**(2) 귀 중점을 입꼬리에 매핑하는 게 애초에 억지였다.** BlazeFace는 입
랜드마크를 하나(중앙점)만 주는데, ArcFace 참조점은 좌/우 입꼬리 두 개다.
`lm[3]`(입 중앙)을 좌측 입꼬리에, 귀 중점을 우측 입꼬리에 우겨넣고 있었다.
귀는 눈 높이 부근이라 입꼬리와는 전혀 다른 위치인데, 이 나쁜 대응관계가
최소자승 피팅을 매 프레임 다른 방향으로 끌고 다녔다 — 이게 회전각이
프레임마다 42°~90°로 들쭉날쭉했던(고정 오프셋이 아니라) 이유였다.

**수정:** 5점 → 4점(눈2+코+입중앙)으로 줄이고, 참조점도 입꼬리 두 개의
중점으로 축소했다.

```dart
// 눈 순서 스왑 + 귀 제거
static List<Point> _pickFourPoints(List<Point> lm) {
  if (lm.length < 5) throw ArgumentError('Need ≥5 landmarks, got ${lm.length}');
  return [lm[1], lm[0], lm[2], lm[3]];
}

// 5점 참조를 4점으로 축소(입꼬리 중점)
static List<Point> _fourPointReference(List<Point> ref5) {
  final mouthMid = Point((ref5[3].x + ref5[4].x) / 2, (ref5[3].y + ref5[4].y) / 2);
  return [ref5[0], ref5[1], ref5[2], mouthMid];
}
```

## 6. 최종 검증 — 실기기 크롭 육안 확인

두 수정(카메라 회전 + 랜드마크 대응)을 모두 적용하고 실기기에서 다시 확인했다.
7개 프레임의 회전각: `22.8° / 15.2° / 17.0° / 15.2° / 7.8° / 17.1° / 18.5°` —
전부 같은 방향, 자연스러운 범위. base64 크롭 덤프를 PNG로 복원해서 직접 봤다 —
**이전엔 창틀/블라인드가 프레임을 채우고 있었는데, 이번엔 안경 낀 얼굴이
프레임 대부분을 채우고 눈-코-입 배치도 정상 방향이었다.**

## 7. 정식 회귀 테스트로 전환

진단용으로 임시로 넣었던 테스트를 정식 회귀 테스트로 재구성했다
(`test/alignment/affine_aligner_test.dart`):

- **항등 케이스**: 동일 점집합 → 단위행렬 (기존 DIAG 테스트를 정식화)
- **Umeyama(1991) §III 논문 예제**: `c=0.72111`, `t=(-0.8,0.4)` 등 발표값과
  1e-3 이내 일치 검증
- **스케일 복원**: ArcFace 참조점을 2.2배 확대+12° 회전한 뒤 다시 맞추면
  `scale=1/2.2`가 정확히(1e-6 이내) 나오는지 검증
- **반사 케이스**: 좌우 미러링된 입력에서도 `det(R)=1`(반사 아님)로 처리되는지
  검증
- **눈 순서 회귀 가드(양방향)**: 실제 BlazeFace 순서(rightEye,leftEye,...)로
  넣으면 항등이 나오고, 옛날처럼 안 뒤집은 순서로 넣으면 항등이 안 나온다는
  것까지 둘 다 고정 — 이번에 고친 버그가 재발하면 반드시 잡히도록 함

새 테스트 훅 `alignmentMatrixForTest()`를 추가해서, `align()`이 실제로 쓰는
계산 경로(4점 추출→기준점 축소→Umeyama)를 이미지/워핑 없이 그대로 테스트할 수
있게 했다. 전체 테스트 스위트는 85개로 늘었고 전부 통과한다.

## 8. 진단 도구 신설

`tool/analyze_alignment_log.py`를 새로 만들었다. `FACEKIT_VERBOSE_DEBUG` 로그를
파싱해서:

- `_cameraQuarterTurns` 값 리포트
- `LANDMARKS`+`DEBUG MATRIX` 쌍마다 회전각·스케일 계산
- 눈 두 점이 세로로 더 벌어짐(90°급 카메라 회전 신호), `a≠d`(반사/SVD 버그
  신호), `|회전각|>45°`, 스케일이 `[0.05, 3.0]` 밖 — 네 가지 이상 징후를
  자동으로 플래그
- `--crops-out` 옵션으로 base64 크롭 덤프를 PNG로 복원

이전에 버그가 있던 상태의 가짜 로그로 테스트하니 두 가지 이슈(세로로 벌어진
눈, 172.6° 회전)를 정확히 잡아내고 exit code 1로 종료되는 것을 확인했다.

이 도구로 더 긴 실사용 세션(26개 검출)을 돌려보니 10개가 플래그됐다(회전
46°~86°). 조사해보니 플래그된 항목들이 무작위가 아니라 짧은 구간에 연속으로
몰려 있었고(#11-13, #23-25), 가장 심한 케이스(#12, 83.6°)를 직접 뜯어보니
코 랜드마크가 눈보다 위쪽에 있었다 — 정렬 계산의 문제가 아니라 **그 순간
BlazeFace 자체가 극단적인 포즈/모션에서 랜드마크를 부정확하게 찍은 것**으로
결론지었다. 코드 버그의 재발이 아니라 가벼운 검출 모델의 고유한 한계다(포즈
게이트 같은 방어 기능은 새 기능이라 이번 범위에서는 안 넣었다 — 6절 참고).

## 9. 유사도·벤치마크 재측정

**유사도** — 실기기에서 enroll 1회 후 identify 46회를 다양한 포즈/거리로
반복했다. 결과: **46회 전부 `accepted=true`**, `min=0.776 max=0.979
mean=0.906 median=0.904`, 임계값(`0.40`)까지 최소 마진 `0.376`. 7/24
포스트모템 기준값(0.81~0.94, 15회)과 비교해도 범위가 비슷하거나 더 넓다(최대
0.979) — **정렬 버그를 고친 게 유사도를 떨어뜨리지 않았다.**

**벤치마크** — Pixel 7 CPU AuraFace 재측정: 검출 45.2ms / 임베딩 1332.1ms /
전체 1378.5ms. 기존 문서 기록(1차 1135.3ms, 2차 1238.1ms)보다 다소 높지만,
검출 시간(정렬 코드와 무관한 경로)도 같이 변동한 걸 보면 **기기 컨디션(발열,
배터리, 백그라운드 앱) 변동**으로 판단했다 — 오늘 고친 건 5~6점짜리 SVD
계산+112×112 워핑이라 ResNet100 임베딩 추론(1초 이상) 대비 계산량이 무시할
수준이라 이 정도 차이를 만들 수 없다.

## 10. 정리 — 버그 네 개의 인과관계

```
버그 1: _svd2x2 vt 부호 뒤집힘        ┐
버그 2: 공분산 /n 정규화 누락          ┤ 코드 리뷰(정적 분석)로 발견,
                                       │ Python 재구현 + 실기기 단위테스트로 확정
                                       ┘

  둘 다 고침 → 실기기 크롭은 여전히 회전/스케일 이상
       │
       ▼
버그 3: 전면 카메라 회전 공식(turns=1이어야 할 걸 turns=2)
  → 랜드마크 좌표 역산 + 4가지 turns 후보 비교로 실측 확정

  고침 → 눈은 가로로 정상화됐지만 회전각 42°~90° 잔존
       │
       ▼
버그 4: 눈 좌우 인덱스 반전 + 귀중점→입꼬리 억지 대응
  → 4점(눈2+코+입중앙)으로 축소 + 눈 인덱스 스왑

  고침 → 크롭 육안 확인 정상, 회전각 7.8°~24.3°(자연스러운 범위)로 수렴
       │
       ▼
최종 검증: 유사도 46/46 accepted, 벤치마크 회귀 없음
```

넷 다 서로 다른 층위(SVD 수학 / 카메라 하드웨어 설정 / 랜드마크 시맨틱)의
버그였고, 겹쳐 있었기 때문에 하나씩 고칠 때마다 "나아졌는데 여전히 이상하다"가
세 번 반복됐다. 7/24 포스트모템의 교훈("두 원인이 겹쳐 있을 가능성을 열어둬야
한다")이 이번엔 네 겹으로 재확인된 셈이다.

## 11. 배운 것

- **정적 코드 리뷰가 잡아낸 건 실제 버그였지만, 예측 목록 자체는 안 미더웠다.**
  6개 사전 예측 중 2개만 적중했고, 가장 심각했던 버그(vt 부호)는 목록에도
  없었다. "주석과 구조가 맞으니 동작도 맞겠지"로는 안 잡히는 종류였다 —
  `U·diag(s)·Vᵀ`를 실제로 곱해서 원본이 나오는지 확인해야만 드러났다.
- **논문 수치 예제가 진단 비용을 극적으로 낮췄다.** `c=0.72111,
  t=(-0.8,0.4)` 같은 검증 가능한 정답이 없었다면 "이 SVD가 맞나?"를 싸게
  물어볼 방법이 없었다. 6단계에서 반복적으로 쓴 "동일한 두 점집합 → 항등행렬"
  명제도 마찬가지로, 논문도 참조 구현도 필요 없는 자명한 오라클이었다.
- **"흔들었나?" "기기를 눕혔나?" 같은 사용자 측 가설을 성급하게 받아들이지
  않고 데이터로 검증한 게 시간을 아꼈다.** 6개 프레임 전부에서 동일한
  기하학적 패턴(dx≪dy)이 재현된다는 것 자체가 무작위 요인(흔들림)을 배제하는
  증거였다.
- **git 이력 확인이 "회귀인가, 놓친 엣지케이스인가"를 빠르게 갈랐다.** 회전
  관련 코드가 7/24 수정 이후 안 바뀌었다는 사실 하나로, "코드가 다시 망가졌다"는
  가설을 접고 "그때 못 잡은 조건이 있다"는 방향으로 바로 좁힐 수 있었다.
- **회전각이 프레임마다 고정 오프셋이 아니라 들쭉날쭉하다는 패턴 자체가
  진단 정보였다.** 카메라 회전(하드웨어 설정) 문제라면 매 프레임 거의 같은
  각도가 나와야 하는데, 실제로는 42°~90°로 흩어져 있었다 — 이게 "랜드마크
  대응관계가 매 프레임 다른 방식으로 어긋나고 있다"는 신호였고, 실제로
  그랬다.
- **크롭 이미지를 실제로 복원해서 보는 것이 결정적이었다는 게 이번에도
  재확인됐다.** 행렬 숫자만 봐도 회전각 이상은 알 수 있지만, "배경 창틀이
  프레임을 채운다"는 사실은 실제 이미지를 봐야만 드러났다 — 7/24 포스트모템의
  8절과 같은 결론이다.

## 미해결로 남긴 것

- **후면 카메라 회전 공식은 여전히 미검증이다.** `turns=2`는 이 기기의 전면
  카메라 실측값이고, 후면 분기는 옛날 공식(`sensorOrientation % 360`) 그대로
  방치했다 — 검증할 방법(후면 카메라 테스트)이 없었다.
- **극단적 포즈에서 BlazeFace 랜드마크 품질이 떨어지는 문제**는 발견했지만
  의도적으로 안 고쳤다. 회전각 기반 포즈 게이트("회전이 너무 크면 그 프레임은
  매칭에 안 씀") 같은 방어 기능은 버그 수정이 아니라 새 기능이라 범위 밖으로
  뒀다.
- 위 두 개와 기존에 미뤄둔 AuraFace impostor-pair 임계값 검증 건을 묶어서
  GitHub 이슈로 등록할 예정이다.
