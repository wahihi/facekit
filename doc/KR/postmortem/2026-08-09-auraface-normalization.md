# 타인도 나로 인식되던 하루 — 원인은 정렬이 아니라 정규화였다

**날짜:** 2026-08-09
**증상:** 타인의 얼굴을 등록한 뒤 실시간 인식을 켜고 타인 본인을 비추면 유사도 0.9대,
그런데 그 상태에서 전혀 다른 사람(등록자 본인)을 비춰도 똑같이 0.9대가 나왔다 —
즉 AuraFace가 서로 다른 두 사람을 사실상 구분하지 못하고 있었다.
**결론(스포일러):** 8/3 포스트모템에서 고친 정렬 버그와는 완전히 무관한, **AuraFace
매니페스트 하나의 설정값(`input.normalize`)이 틀려 있었다.** 정규화 없이 원본
0~255 픽셀을 그대로 넣고 있었는데, 이건 공식 `insightface` 패키지가 이 모델
그래프를 보고 자동으로 채택하는 값(`(pixel-127.5)/127.5`)과 달랐다. 흥미로운 건 이
틀린 값 자체가 **7/24 포스트모템에서 정렬 버그와 뒤섞여 잘못 진단된 결과물**이었다는
것 — 8/3에 정렬을 고친 뒤에도 아무도 정규화 값을 재검증하지 않아서 한 달 넘게
틀린 채로 남아있었다.

이 프로젝트는 [Claude Code](https://github.com/anthropics/claude-code)와 협업해서
개발했고, 이 디버깅도 마찬가지다 — 틀린 가설과 몇 번이나 실패한 실기기 로그
캡처 시도까지 그대로 남겨둔다.

## 0. 증상 재현

타인의 얼굴을 등록한 뒤 "실시간 인식 시작"을 켜고 카메라에 타인 본인을 비추면
유사도 0.9% 정도가 나왔다. 그런데 그 상태에서 완전히 다른 사람(등록한 계정
소유자 본인)을 비춰도 똑같이 0.9%가 나왔다 — 등록/실시간 인식 파이프라인
어딘가가 두 사람을 구분하지 못하고 있다는 신호였다.

## 1. 첫 번째 용의선상: 실시간 인식 로직 자체?

`main.dart`의 `_onFrame` 흐름(검출 → 라이브니스 → `pipeline.identify`)을 다시
검토했지만, 매 프레임 실제 라이브 이미지로 새로 임베딩을 계산하고 있었고 캐시된
이미지를 재사용하는 버그는 없었다. 라이브니스(블링크 확인) 게이트가 테스트를
방해하고 있었던 것도 문제였다 — 노트북 화면에 띄운 사진으로는 눈을 깜빡일 수
없으니, `_kSkipLivenessForDebug` 플래그를 임시로 추가해 게이트를 우회하고 정지
사진으로도 identify가 바로 실행되게 했다(이후 원복, 4절 참고).

## 2. 두 번째 용의선상: 정렬(alignment) 회귀

`flutter run --dart-define=FACEKIT_VERBOSE_DEBUG=true`로 실기기 로그를 받아
`tool/analyze_alignment_log.py`로 분석하니, 46개 검출 중 13개(28%)가 회전각
55°~170°로 플래그됐다 — 8/3 포스트모템이 고쳤다고 검증했던 바로 그 실패
패턴(BlazeFace 랜드마크가 극단적 포즈에서 흔들리는 문제, 8/3 문서의 "미해결로
남긴 것"에 이미 예견돼 있었다)이 그대로 재현된 것이었다. 정렬된 크롭을 base64
덤프에서 PNG로 복원해서 보니 실제로 얼굴이 대각선으로 기울고 배경(창틀/블라인드)이
크게 섞인 나쁜 크롭들이 확인됐다.

그런데 결정적인 반례가 나왔다: **회전이 정상(20.8°, 31.9°, "ok" 판정)인 깨끗한
크롭에서도 서로 다른 두 사람이 똑같이 0.83~0.88로 매칭됐다.** 정렬 품질과 무관하게
오탐이 발생한다는 뜻이었다 — 정렬은 범인이 아니었다(적어도 주범은 아니었다).

## 3. 대조 실험 — ArcFace로 교체

같은 파이프라인(검출·정렬은 임베더와 완전히 독립된 코드)에서 임베더만 AuraFace →
ArcFace(`buffalo_l`)로 바꿔 같은 조건(본인 등록 → 본인/타인 비교)을 재현했다.
ArcFace는 **회전이 오히려 더 나쁜 조건(128.1°, FLAGGED)에서도 타인을 정확히
거부**(유사도 0.391, threshold 0.40 미만)했고, 본인은 0.67~0.97로 명확히 갈랐다.
같은 detect/align 코드, 같은 실기기 조건에서 임베더만 바꿨는데 결과가 갈렸다는
것은, **정렬/검출이 아니라 AuraFace 임베더 자체에 문제가 있다**는 강력한 증거였다.

## 4. AuraFace 모델 자체가 약한가? — 공식 구현체로 교차검증

AuraFace(glintr100)는 ArcFace와 같은 계열(ResNet100, Additive Angular Margin
Loss) 모델이라 원래 판별력이 떨어질 이유가 없었다. fal.ai의 공식 README와
InsightFace의 `ArcFaceONNX` 소스(`model_zoo/arcface_onnx.py`)를 웹에서 찾아보니,
전처리 방식이 **고정 스펙이 아니라 ONNX 그래프의 첫 8개 노드 이름을 보고 자동
판별**하는 방식이었다:

```python
if find_sub and find_mul:      # 그래프에 정규화가 이미 내장됨(MXNet 익스포터 패턴)
    input_mean, input_std = 0.0, 1.0
else:                            # 정규화가 안 내장됨 → 표준 값 적용
    input_mean, input_std = 127.5, 127.5
```

새로 만든 `tool/model_verification/verify_auraface_official.py`(공식 `insightface`
패키지의 검출+정렬+임베딩 전체를 그대로 씀, facekit Dart 코드는 전혀 안 거침)로
실제 `glintr100.onnx`를 로드해보니, 로그에 이렇게 찍혔다:

```
find model: ./models/auraface/glintr100.onnx recognition ['None', 3, 112, 112] 127.5 127.5
```

**127.5, 127.5** — 표준 ArcFace 정규화였다. 그리고 이 값으로 본인 사진 2장 +
타인 사진 1장을 테스트하니 genuine 0.7737 vs impostor 0.0257/-0.0266으로
극적으로 갈렸다. **AuraFace 모델 자체는 전혀 약하지 않았다.**

## 5. facekit과 공식 구현체의 차이 — 매니페스트 정규화 값

`example/assets/models/auraface/manifest.json`을 확인하니:

```json
"normalize": { "mean": [0.0, 0.0, 0.0], "std": [1.0, 1.0, 1.0] }
```

정규화가 아예 없는(raw 0~255 픽셀 그대로) 설정이었다 — 공식 값(127.5/127.5)과
정반대였다.

## 6. 왜 틀린 값이 들어갔는가 — 7/24 포스트모템과의 인과관계

7/24 포스트모템 기록을 다시 보면, 그날 "정규화 없이 raw로 넣어야 자기-유사도가
0.93, 표준 정규화로는 0.15~0.20"이라고 결론 내리며 raw 값을 채택했다. 그런데 **그
시점에는 정렬 파이프라인에 아직 안 고쳐진 버그(눈 좌우 순서 반전, SVD 부호 오류,
공분산 `/n` 누락)가 있었다** — 이 버그들은 한 달 뒤인 8/3에야 고쳐졌다. 즉 7/24에
비교했던 "정렬된 크롭"은 이미 잘못 회전된 상태였고, 그 나쁜 크롭에 표준 정규화를
걸었더니 유사도가 낮게 나온 것을 "정규화가 틀렸다"로 오진단하고 raw pixel로
바꿔서 우연히 봉합한 것으로 보인다. 8/3에 정렬 버그를 고친 뒤, 아무도 정규화
설정을 다시 검증하지 않아서 raw 값이 그대로 남아있었다.

## 7. 수정 및 실기기 재검증

`input.normalize`를 표준값으로 고쳤다:

```json
"normalize": { "mean": [127.5, 127.5, 127.5], "std": [127.5, 127.5, 127.5] }
```

실기기에서 본인 등록 후 일론 머스크 사진(모니터 화면 재촬영)으로 재테스트했다.
정렬된 크롭을 프레임마다 전부 덤프하도록 `_debugDumpAlignedFace`를 임시로
바꿔서(이후 원복) 실제로 무엇이 모델에 들어가는지 직접 확인했다 — 여러 번의
로그 캡처 시도가 `q` 종료 타이밍과 마지막 프레임 덤프가 겹쳐 청크가 잘리는
문제로 실패한 끝에, 마침내 깨끗한 일론 머스크 크롭 4장을 확보했다: 유사도
**0.060~0.094**, 전부 명확히 거부됐다. 본인 얼굴은 여전히 threshold를 넘겼다.

## 8. LFW 200쌍으로 정식 threshold 도출

즉석 3장 테스트(genuine 0.77 vs impostor ≈0.03)는 표본이 작아 우연히 잘 갈린
결과일 수 있어서, ArcFace/AdaFace 때와 동일한 방법론(`compare_arcface_adaface.py`에
`--auraface-tflite` 옵션 추가, LFW 200쌍, seed=42, 5점 정렬 미적용 리사이즈만)으로
정식 재측정했다:

| 모델 | 조건 | genuine 평균 | impostor 평균 | EER | EER 임계값 | 해당 임계값 정확도 |
|---|---|---|---|---|---|---|
| AuraFace | clean | 0.4803 | 0.1952 | 10.0% | 0.300 | 90.0% |
| AuraFace | degraded | 0.3560 | 0.2402 | 28.0% | 0.274 | (clean 임계값 적용 시 68.5%) |

ArcFace(EER 8.5%)와 비슷한 수준이고 AdaFace(EER 2.0%)보다는 뚜렷이 낮다 — 셋 중
가장 약한 판별력이지만, "구분을 아예 못 한다"는 처음 증상과는 완전히 다른
상태다. `matching.threshold`를 무근거 placeholder(0.40)에서 실측값(0.30)으로
갱신했다. 실기기 재검증(본인 얼굴만, threshold 0.30)에서는 11번 중 8번(73%)
accept — LFW 정확도(90%)보다 낮았는데, 정제된 LFW 사진과 달리 손으로 든 셀피
(안경 반사, 각도, 조명)라 실측 조건이 더 가혹했기 때문으로 보인다. 사용성과
보안의 트레이드오프이므로 이 값을 더 낮출지는 별도 판단이 필요하다.

## 9. 정리 — 인과관계

```
7/24: 정렬 버그가 있는 상태에서 AuraFace 정규화를 진단
   └→ 잘못 회전된 크롭 + 표준 정규화 = 낮은 유사도로 오진단
   └→ raw pixel(무정규화)로 "수정" — 증상은 없어졌지만 원인은 안 고쳐짐

8/3: 정렬 버그 4개를 전부 고침 (7/24와 무관한 별도 조사)
   └→ 동일인 유사도만 재검증(0.776~0.979) — 정규화 값은 재검증 안 함
   └→ raw pixel 설정이 그대로 남음

8/9: 실사용 중 타인 오탐 재현
   └→ 정렬 회귀 의심 → 대조 실험(ArcFace)으로 배제
   └→ 공식 insightface 패키지 교차검증 → 정규화 값이 틀렸음을 확정
   └→ 표준값(127.5/127.5)으로 수정 → 실기기 재검증(0.06~0.09) + LFW 200쌍
      재측정(threshold 0.30)으로 정식 확정
```

## 10. 배운 것

- **"임계값처럼 재튜닝이 필요해 보이는 값"만 의심해선 안 된다.** `input.normalize`
  같은 "정답이 하나뿐인 것처럼 보이는" 설정값도, 그 값을 처음 정한 시점에 다른
  버그(이번엔 정렬)가 섞여 있었다면 틀린 채로 굳어질 수 있다. 값 하나를
  재검증할 땐 그 값이 결정된 시점의 전제(여기선 "크롭이 똑바로 정렬돼 있다")도
  같이 의심해야 한다.
- **대조군을 바꿔보는 게 원인을 층으로 갈라낸다.** "회전이 나쁜데도 타인을
  정확히 거부하는 임베더(ArcFace)"와 "회전이 좋은데도 타인을 못 거르는
  임베더(AuraFace)"를 나란히 놓고 보니, 회전(공통 코드)이 범인이 아니라
  임베더(교체된 부분)가 범인이라는 게 바로 드러났다. 같은 대조군을 계속
  유지하는 게 7/24, 8/3 포스트모템에서도 결정적이었는데, 이번엔 "대조군을
  바꿔보는 것" 자체가 결정적이었다.
- **모델이 의심스러우면 서드파티 SDK가 아니라 공식 구현체까지 내려가서
  대조하라.** facekit의 어댑터 코드나 매니페스트만 들여다봐서는 "표준
  컨벤션이 뭔지" 확신할 수 없었다 — InsightFace의 실제 소스 코드(그래프
  노드 이름을 검사하는 자동판별 로직)까지 내려가서야 정답이 나왔다.
- **실기기에서 원하는 프레임 하나를 로그로 잡는 것도 만만치 않다.** `q`로
  종료하는 타이밍이 마지막 identify() 호출의 base64 덤프와 겹치면 청크가
  잘려서 크롭을 복원할 수 없다 — 몇 번의 시도 끝에 "원하는 장면을 비춘 뒤
  충분히(5초 이상) 기다렸다가 종료"해야 한다는 걸 배웠다. 사소해 보이지만
  이것 때문에 결정적 증거(일론 머스크 크롭) 확보가 세 번이나 미뤄졌다.

## 부록: 남겨둔 도구

- `tool/model_verification/verify_auraface_official.py` — 공식 `insightface`
  패키지로 genuine/impostor 유사도를 즉석에서 확인하는 신규 스크립트. 매번
  전체 LFW 측정을 돌리기 부담스러울 때, 사진 몇 장으로 빠르게 감을 잡는 용도로
  남겨둔다.
- `tool/model_verification/compare_arcface_adaface.py`에 `--auraface-tflite`
  옵션 추가 — ArcFace/AdaFace와 동일한 LFW 200쌍 방법론을 AuraFace에도 그대로
  적용할 수 있다. 각 모델 플래그가 독립적이라 하나만 골라 돌릴 수도 있다.
- `lib/src/pipeline/face_pipeline.dart`의 매 프레임 크롭 덤프(임포스터 프레임을
  직접 보기 위해 임시로 "라벨당 1회"에서 "매 identify() 호출마다"로 바꿨던 것)는
  조사가 끝난 뒤 원래대로 되돌렸다 — 라이브 세션이 길어지면 로그가 프레임당
  ~37KB씩 불어나기 때문에 기본값으로 남겨두기엔 부적절하다.
