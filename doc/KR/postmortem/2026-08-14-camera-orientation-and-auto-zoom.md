# 화면은 항상 정상으로 보였다 — ML 파이프라인만 몰래 다른 회전을 쓰고 있었다

**날짜:** 2026-08-14
**계기:** [2026-08-13-landmark-jitter-frame-fill.md](2026-08-13-landmark-jitter-frame-fill.md)
에서 만든 2-pass 리파인먼트를 실기기에서 검증하던 중, 사용자가 우연히 "카메라를
가로로 들고 등록하라"는 안내 문구를 보고 실제로 가로로 들었더니 — 리파인먼트가
거의 발동하지도 않았는데(191프레임 중 1번) 등록/인식이 극적으로 안정됐다
(유사도 0.69~0.873, 17/17 accepted, 이전 세션들은 0.13~0.87로 요동치고 오거부도
잦았음). **결론(스포일러):** 원인은 리파인먼트가 아니라 카메라 프리뷰(사용자가
보는 화면)와 ML 파이프라인(실제로 인식에 쓰이는 프레임)이 **서로 다른 회전
로직**을 쓰고 있었다는 것 — 프리뷰는 실시간 기기 방향 센서를 따라가며 항상
정상으로 보이지만, ML 경로는 "세로로 든다"고 가정한 고정값 하나만 썼다. 즉
사용자는 화면이 멀쩡해 보이니 문제를 알아챌 방법이 없었고, 얼마나 자주 이
불일치가 실제로 일어났는지도 검증 못 했다. 이 발견을 시작으로 자동 줌 버그
2개(진동, 방향 부호 반전), "속도가 느려서"라는 잘못된 가설, 검출 신뢰도가
임계값 근처에서 흔들리는 진짜 원인, 그리고 최종적으로 가운데 정사각형
크롭이라는 판단이 필요 없는 근본 대응까지 이어졌다 — **최종적으로 세로
74.6%, 가로 90% accepted, 리파인먼트 실기기 첫 성공까지 확인됐다(13번
참고).**

이 프로젝트는 [Claude Code](https://github.com/anthropics/claude-code)와
협업해서 개발했고, 이 세션도 마찬가지다.

## 1. 발단 — "가로로 들고" 안내 문구를 실제로 따라해봤다

`example/lib/main.dart`에는 초기화 완료 시 딱 한 번 뜨는 안내 문구가 있었다:
`'준비 완료 — 카메라를 가로로 들고 "등록"을 눌러보세요.'`. 지금까지 세션들은
거치대에 세로로 세워두고 테스트해왔는데, 사용자가 이 문구를 발견하고 실제로
손으로 폰을 가로로 쥐고 테스트했더니 — 멀든 가깝든 등록/인식이 갑자기 훨씬
잘 됐다.

## 2. 1차 가설(틀림) — "이번 세션이 덜 흔들렸다"

처음엔 "거치대(고정) → 손으로 쥠(더 흔들림)인데 오히려 좋아졌다는 게 이상하다"는
사용자 지적을 받고서야, "흔들림이 덜해서"라는 내 추측이 틀렸다는 걸 인정했다.
거치대에서 손으로 옮기면 흔들림은 **늘어야** 정상인데 결과는 반대였다 — 흔들림
가설로는 설명이 안 됐다.

## 3. 로그로 확인한 진짜 차이 — 리파인먼트가 아니라 애초에 얼굴이 컸다

가로로 든 세션(`log1.txt`)의 얼굴/프레임폭 비율을 뽑아보니:

| 지표 | 가로 파지 (log1.txt) | 이전 세션들 |
|---|---|---|
| 얼굴 비율 평균 | **41.8%** | 15~30%대에서 요동 |
| 30~59% 구간 비율 | 191개 중 152개 | 20% 경계 근처에서 극심한 변동 |
| 리파인먼트 발동 | 191번 중 **1번** | 자주 발동 |
| 유사도 | **0.69~0.873**, 평균 0.833 | 0.13~0.87로 요동 |
| identify 결과 | **17/17 accepted** | 오거부 다수 |

리파인먼트가 *거의 작동을 안 했는데도* 결과가 압도적으로 좋았다 — 즉 원인은
소프트웨어 크롭 로직이 아니라, **얼굴이 애초에 훨씬 크게 캡처되고 있었다**는
것.

## 4. 왜 가로로 들면 얼굴이 커지나 — 회전 경로가 두 개였다

`example/lib/face_overlay.dart`의 헤더 코멘트를 다시 읽다가 결정적인 문장을
발견했다: `CameraController.startImageStream`은 프레임을 **센서의 raw
방향**으로 넘기고, `CameraPreview` 위젯은 **`CameraValue.deviceOrientation`
(실시간 기기 방향 센서)**을 따라가는 별도의 회전을 적용해서 화면에 그린다 —
`quarterTurnsForOrientation()` 함수가 그 역할을 한다.

그런데 `main.dart`의 `_cameraQuarterTurns()`(ML 파이프라인에 넘기는 프레임을
회전시키는 함수)는 카메라 하드웨어의 **고정값**(`sensorOrientation`)만 보고
계산되는, "기기가 항상 세로로 들려 있다"고 가정한 **정적인** 값이었다 — 실시간
방향 센서를 전혀 안 봤다.

즉 프리뷰(사용자가 보는 화면)는 항상 정상으로 보이도록 자동 보정되는데, ML
경로(실제 인식에 쓰이는 프레임)는 "세로로 들었을 때"만 맞는 고정 회전을 계속
썼다. 사용자가 폰을 어떻게 쥐든 화면은 늘 멀쩡해 보이니, **정작 인식에 쓰이는
프레임이 잘못된 방향일 수 있다는 걸 알아챌 방법이 전혀 없었다.**

카메라 센서 자체의 시야각이 한쪽으로 더 넓다는 걸 감안하면: 앱이 가정한
"세로 파지"로 들면 그 넓은 축이 좌우(수평)로 눕게 되어 얼굴 양옆에 불필요한
배경이 많이 잡히고(얼굴/프레임폭 비율 낮음), 반대로 가로로 들면 넓은 축이
상하로 눕게 되어 프레임 폭 방향으로는 훨씬 좁은 시야각만 남아 얼굴이 더 크게
찍힌다 — 지금까지 계속 추적해온 "얼굴/프레임폭 비율" 문제가 순전히 물리적
파지 방향 때문에 널뛰기하고 있었던 것.

## 5. 수정 — ML 경로도 실시간 방향 센서를 반영하게

`_cameraQuarterTurns()`를 고정값 하나가 아니라, **기존에 검증된 고정
보정값(portraitUp 기준, Pixel 7 실측)** + **프리뷰가 이미 쓰고 있던 것과 같은
`quarterTurnsForOrientation(liveOrientation)` 델타**의 합으로 바꿨다:

```dart
final turns = (_baseQuarterTurns + orientationDelta) % 4;
```

`_baseQuarterTurns`는 기존 고정 계산을 그대로 보존(= portraitUp일 때는 이전과
100% 동일 동작, 회귀 없음)하고, `orientationDelta`는 프리뷰 오버레이가 이미
신뢰하고 쓰던 함수를 재사용했다(직접 새 공식을 유도하지 않음 — 실기기 접근이
없는 상태에서 회전 방향 부호를 새로 유도하는 건 검증 불가능한 도박이라 판단).

**부작용 하나 발견**: ML 이미지가 이제 이미 방향 보정된(업라이트) 상태로
나오므로, 오버레이 페인터가 *추가로* `quarterTurnsForOrientation`을 또
적용하면 이중 회전이 된다 — `main.dart`의 `FaceOverlayPainter` 호출부를
`quarterTurns: 0`으로 같이 고쳤다. (이전 코드에서 이게 우연히 안 터진 이유:
`portraitUp`일 때 `quarterTurnsForOrientation`이 0을 반환해서 이중 회전이
"0 + 0"으로 눈에 안 띄었을 뿐 — 세로가 아닌 다른 방향에서는 이전에도 오버레이
박스가 실제 얼굴과 어긋났을 가능성이 있다.)

**중요 — 이 수정은 실기기 검증 전이다.** 회전 방향 부호(시계/반시계)를 실제
기기 없이 코드만으로 확정할 수 없어서, 기존에 이미 실측·신뢰된 함수를
재사용하는 가장 보수적인 방법을 택했지만, 그래도 실기기에서 **portraitUp
(회귀 없는지) + 다른 3방향 전부**를 확인해야 한다.

## 6. 추가 조치 — 카메라 레벨 자동 줌

리파인먼트(소프트웨어 크롭)의 근본적 한계도 이번에 명확해졌다: 카메라가
`ResolutionPreset.medium`으로 이미 720×480으로 다운샘플해서 넘기므로, 그
이후 아무리 잘 크롭해도 카메라가 애초에 버린 디테일은 못 살린다. 반면
`CameraController.setZoomLevel()`은 **캡처 자체**를 센서 원본 해상도 기준으로
좁혀서 가져오므로, 진짜 해상도 이득이 있다.

매 프레임 얼굴 비율을 보고 30~60% 구간을 벗어나면 줌을 조금씩 조정하는
피드백 루프를 추가했다(`_maybeAdjustZoom`, 400ms 쿨다운 + 고정 스텝으로 매
프레임 줌을 헌팅하지 않게 함). 줌이 이미 최대인데도 얼굴이 작으면(사용자가
너무 멀리 있음) `_framingHint`라는 상시 노출 안내 문구("카메라에 조금 더
가까이 와주세요")를 띄운다 — 기존의 "가로로 들고" 안내는 `_status`에 딱 한
번만 찍히고 다른 메시지에 덮여 사라지는 구조라 사실상 무용지물이었던 것도
같이 고쳤다.

## 7. 정리 — 인과관계

```
질문: 리파인먼트가 거의 발동 안 했는데 왜 가로로 들면 결과가 극적으로 좋아지나?
   └→ 1차 가설(사용자가 반박): "이번 세션이 덜 흔들렸다" — 거치대→손 파지인데 오히려 좋아진 것과 모순, 기각
   └→ 로그 분석: 얼굴/프레임폭 비율이 평균 15~30%대(요동)에서 41.8%(안정)로 실제로 커짐
   └→ face_overlay.dart 재검토: 프리뷰는 실시간 deviceOrientation을 따라가는데, ML 경로(_cameraQuarterTurns)는 고정값만 사용
   └→ 가설: 사용자가 실제로 어떻게 쥐든 화면은 항상 정상으로 보이지만, ML 프레임은 "세로 파지" 가정이 깨지면 잘못된 방향일 수 있음
   └→ 수정: ML 경로도 같은 실시간 방향 델타(quarterTurnsForOrientation)를 반영하도록 변경
        └→ 부작용 발견: 오버레이가 이제 이중 회전 — quarterTurns: 0으로 수정
   └→ 추가: 카메라 레벨 자동 줌 + 상시 노출 프레이밍 안내 문구
   └→ 아직 안 함: 실기기에서 4방향(portraitUp/Down, landscapeLeft/Right) 전부 검증
```

## 8. 배운 것

- **"화면이 정상으로 보인다"는 "처리 파이프라인이 정상"이라는 증거가 아니다.**
  프리뷰와 ML 경로가 서로 다른 코드로 회전을 계산하면, 사용자에게 보이는
  피드백(화면)과 실제로 모델이 받는 입력이 완전히 다를 수 있다 — 그리고 그
  차이는 화면만 봐서는 절대 알 수 없다. 두 경로가 같은 소스(실시간
  deviceOrientation)를 공유하게 만드는 게 가장 안전하다.
- **가설이 사용자의 직접 반박으로 기각됐을 때, 그 반박 자체가 다음 단서다.**
  "흔들림이 덜해서"가 "거치대에서 손 파지로 바뀌었는데 흔들림이 줄었을 리
  없다"는 사용자의 한 마디로 무너졌고, 그 지적이 "그럼 진짜 뭐가 다른가"라는
  올바른 질문으로 이어졌다.
- **소프트웨어 크롭(post-capture)과 카메라 레벨 줌(pre-capture)은 근본적으로
  다르다.** `ResolutionPreset` 같은 캡처 단계의 해상도 제한은, 그 이후
  단계에서 아무리 똑똑하게 크롭해도 못 넘는 상한선이다. 이미지 품질 문제를
  풀 때는 "어느 단계에서 정보가 이미 손실됐는가"부터 확인해야 한다.
- **안내 문구가 `_status`처럼 다른 메시지에 계속 덮이는 단일 상태 변수에
  얹혀 있으면, 사실상 아무도 못 본다.** 지금까지 몇 세션 동안 정답이
  화면에 한 번 스쳐 지나갔을 뿐이었다 — 중요한 지속적 안내는 별도의,
  다른 메시지에 안 덮이는 상태로 분리해야 한다.
- **한 번도 실기기에서 못 돌려본 회전 공식은 "그럴듯함"이 아니라 "검증
  대기"로 표시해야 한다.** 이미 신뢰된 함수(프리뷰의
  `quarterTurnsForOrientation`)를 재사용해서 리스크를 최소화했지만, 그래도
  4방향 전부 확인 전까지는 이 문서도, 코드 주석도 "완료"가 아니라 "가설+
  최선의 보수적 구현"으로 남겨둔다.

## 9. 실기기 1차 검증 — 자동 줌이 진동했다

`log2.txt`(2026-08-14 16:30)로 처음 실기기에서 돌려보니, "계속 인식했다가
말았다가 반복된다"는 증상이 나왔다. 사용자가 "차라리 BlazeFace 4점 + 디지털
줌으로 가는 게 낫지 않나"라고 물어서 로그를 봤는데, 원인은 디텍터가 아니라
**자동 줌 제어 루프 자체가 진동**하고 있었다:

```
zoom=1.20 → faceFraction=0.679 (68%, 목표 30~60% 초과)
zoom=0.90 → faceFraction=0.249 (25%, 목표 미달)
zoom=1.20 → faceFraction=0.719 (72%, 또 초과)
zoom=0.90 → faceFraction=0.270 (27%, 또 미달)
```

목표 구간(30~60%)에 단 한 번도 안착하지 못하고 매번 반대 방향으로 튕겨나갔다.
이 진동 구간과 `accepted=false` 몰린 구간이 거의 겹쳤고, 반대로 줌이 안 흔들린
구간(2134~2880번 줄)은 8번 연속 대부분 accepted=true였다 — 줌이 안정적일 때만
인식도 안정적이라는 뜻.

원인 두 가지가 겹쳤다: (1) 쿨다운 400ms가 이 기기의 실제 줌 안정화 시간보다
짧아서, 다음 프레임이 아직 반영 안 된 이전 줌 상태를 보고 계속 반응·과잉교정
했다. (2) `getMinZoomLevel()`이 1.0 미만(0.8958...)을 반환했는데, 1.0 근처는
많은 기기에서 **초광각 렌즈로 물리적 전환**되는 경계라 화각이 불연속으로
뛴다 — `zoom=0.90→1.20`(33% 증가)일 뿐인데 `faceFraction`이 28%→65%로 뛴 게
바로 이 경계를 넘어서였다.

**BlazeFace로 바꾸는 대신 줌 제어 루프를 고쳤다** — 이 진동은 디텍터보다 더
앞단(카메라 캡처 자체)에서 벌어지므로 디텍터를 바꿔도 똑같이 겪었을 것이다:

- `_minZoom`을 1.0 미만으로 안 내려가게 클램프(렌즈 전환 경계 회피)
- 쿨다운 400ms → 900ms(관측된 지연보다 길게)
- 스텝 0.3 → 0.15(오버슈트 완화)
- 연속 3프레임 이상 같은 방향으로 벗어나야 반응(한 프레임 노이즈로 재반응 안 함)

이것도 아직 실기기 검증 전이다 — 다음 테스트에서 줌이 실제로 안착하는지
확인 필요.

## 10. 실기기 2차 검증 — 줌 방향 부호가 반대였다

`log3.txt`(2026-08-14 16:48)로 다시 돌려보니, 사용자가 "얼굴을 가까이 가도
줌인을 해버린다"고 지적했다. 확인해보니 9번에서 진동을 잡으려고 넣은
히스테리시스 로직에서 **방향 부호를 반대로 넣은 버그**였다:

```dart
final direction = faceFraction < _targetFaceFractionLow ? -1   // 작음 → -1(줌아웃 방향)
    : faceFraction > _targetFaceFractionHigh ? 1 : 0;            // 큼 → +1(줌인 방향)
```

얼굴이 이미 목표(30~60%) 훨씬 위인데도(66~95%) 줌이 세션 내내 한 번도
안 내려가고 1.15→3.40까지 계속 올라갔다 — 95.5%(거의 얼굴만 가득)까지 간
프레임도 있었다. `direction`의 삼항 결과를 반대로 고쳤다(작음→+1/줌인,
큼→-1/줌아웃). 9번에서 고친 `_minZoom` 1.0 클램프는 이번 로그에서
`range 1.0-10.0`으로 정상 작동이 확인됐다 — 이번 버그는 그거랑 별개로
같은 리팩토링에서 새로 생긴 것이었다.

같은 세션에서 라이브니스도 재검토했다: EAR 값 238개 중 0.2 미만(눈 감김
판정)은 2번(0.8%)뿐이었고 `blinkCount=1` 도달도 13번뿐 — EAR 신호 자체는
정상이고, 단지 이 세션 동안 사용자가 실제로 깜빡인 순간이 적었던 것으로
보인다. 여기에 `face lost`가 37번 겹쳐서(그때마다 진행 중이던 블링크가
리셋됨), 라이브니스가 인식 안정성 문제와 뒤섞여 원인 분리를 어렵게
만들고 있었다. 인식 자체의 안정성만 먼저 검증하기 위해, 임시로
`_kLivenessEnabled = false` 컴파일타임 플래그로 블링크 게이트 자체를
끄고(매 프레임을 즉시 `passed`로 취급, `MediaPipeFaceLandmarker.
detectLandmarks`도 호출 안 함) 인식 안정성이 별도로 확인되면 다시 켜기로
했다.

## 11. 타이밍 로그로 "느려서 그런가?" 가설 기각, 그리고 진짜 원인

라이브니스를 끈 상태로 다시 실기기(`log4.txt`)를 돌려서, "가만히 있으면
검출이 안 되고 움직이면 되는" 현상이 identify()의 중복 detect() 때문에
프레임 처리가 느려진 탓인지 확인해봤다. 결과는 아니었다 — `onFrame` 처리
시간은 대부분 43~99ms(중앙값 55ms)로 빨랐고, 이 세션엔 `pipeline.
identify()` 호출 자체가 한 번도 없었다(그래서 이 세션은 애초에 진짜 인식
데이터가 없었다는 것도 같이 확인됨).

대신 `face found` 전환 시점의 점수를 보니 원인이 보였다: 0.450~0.532로
검출 임계값(`score_threshold=0.45`) 바로 위에 몰려 있었다. 이 정도면
프레임 간 평범한 센서 노이즈만으로도 점수가 임계값 아래위로 왔다갔다
하면서 찾음/잃음이 반복된다 — 2026-08-12 포스트모템에서 BlazeFace로 처음
발견했던 "임계값 근처 flicker"와 같은 종류의 문제가, 이번엔 YuNet에서
"거리가 멀 때"라는 다른 조건으로 나타난 것. 그리고 자동 줌은 정확히 이
구간(불안정한 검출)에서 판단을 내려야 하니, 필요한 곳에서 오히려 잘
작동을 못 하는 닭과 달걀 구조라는 것도 이때 명확해졌다.

## 12. 근본 대응 — 1차 패스 자체를 가운데 정사각형 크롭으로

사용자 제안으로, 리파인먼트(2차 패스, bbox 기반)와는 별개로 **1차 패스 자체를**
프레임 전체가 아니라 **가운데 정사각형 크롭**으로 바꿨다(`centerSquareCropRegion`,
`lib/src/detection/yunet_decoder.dart`). 720×480 프레임 기준으로:

- 기존: x축 4.5배, y축 3배로 비대칭 squeeze (얼굴이 옆으로 살짝 찌그러짐)
- 신규: 가운데 480×480 크롭 → 양축 다 3배로 균일 squeeze, 왜곡도 없음
- 15% 크기 얼굴 기준, 모델이 보는 얼굴 폭이 24px → 36px로 50% 증가

이 방식이 리파인먼트보다 나은 근본적인 이유: **이전 검출 결과에 전혀 의존하지
않는다.** 리파인먼트는 1차 bbox 주변을 크롭하는데, bbox가 부정확한
(얼굴이 작아서 불안정한) 바로 그 상황에서 크롭이 얼굴을 빗나가기 쉽다 —
실제로 지금까지 실기기에서 리파인먼트가 발동한 5번 전부(확인된 4번)
`fallback`(2차 크롭에서 못 찾음)이었다, **적용 성공 사례가 실기기에서
단 한 번도 없었다.** 가운데 크롭은 판단이 필요 없어서(그냥 항상 가운데를
자름) 이 실패 패턴을 물려받지 않는다. 크롭에서 못 찾으면 원본 전체
프레임으로 폴백한다(얼굴이 화면 중앙에서 많이 벗어난 경우 대비).

예제 앱(`example/lib/face_overlay.dart`, `main.dart`)에는 이 크롭 영역과
정확히 일치하는(약간의 여유를 둔, 85%) 점선 가이드 박스 + "이 안에 얼굴을
맞춰주세요" 안내를 카메라 프리뷰에 항상 표시하도록 추가했다 — 얼굴 검출
여부와 무관하게 항상 보이므로, 첫 검출 전에도 사용자가 어디에 얼굴을
둬야 할지 알 수 있다.

리파인먼트의 100% fallback 원인 규명을 위해 fallback 로그에 크롭 영역
좌표와 1차 bbox를 같이 남기도록 로그도 보강했다 — 다음 실기기 테스트에서
크롭이 실제로 얼굴을 빗나가고 있는지 확인 가능.

## 13. 실기기 최종 검증 — 세로/가로 둘 다 확인, 리파인먼트 첫 성공

**세로 (`log5.txt`, 2026-08-14 18:49).** 가운데 크롭 + 가이드 박스를 넣은 뒤
첫 실기기 테스트. 결과:

- `CENTERCROP hit` 201번 / `fallback` 143번 (적중률 58%) — fallback은 세션
  초반(사용자가 가이드 박스 안에 아직 자리를 못 잡았을 때)에 몰려 있고,
  이후로는 hit이 훨씬 잦았다.
- **리파인먼트가 실기기에서 처음으로 성공했다** — 발동 2번, **2번 다 적용**
  (fallback 0번, 지금까지 5번 발동에 5번 fallback이던 것과 대비):
  ```
  REFINE applied: score 0.457 -> 0.759, face fraction 18.2% -> 37.3%
  ```
  가운데 크롭이 1차 검출 자체를 더 정확하게 만들어주니, 그 bbox를 기반으로
  하는 리파인먼트도 이제 제대로 작동한다는 가설이 실측으로 확인됐다.
- `match:` 71번, **53/71 (74.6%) accepted**. 거부된 것들도 대부분 0.13~0.21로
  임계값(0.211) 바로 아래에 몰려 있어 완전히 엉망은 아니었다. 유사도
  평균 0.279, 표준편차 0.104.

**가로 (`log6.txt`, 2026-08-14 19:04, `landscapeRight`).** 방향 센서 대응도
`liveOrientation=DeviceOrientation.landscapeRight orientationDelta=1 turns=3`
(세로의 turns=2와 다름)으로 정상 작동 확인. 결과가 세로보다 더 좋았다:

| 지표 | 세로 (log5) | 가로 (log6) |
|---|---|---|
| 유사도 평균 | 0.279 | **0.489** |
| identify accepted율 | 74.6% (53/71) | **90% (18/20)** |
| REFINE | 2/2 성공 | 1/1 성공 |
| CENTERCROP 적중률 | 58% | 32.7% (그런데도 결과는 더 좋음) |

가로가 더 나은 이유는 3번에서 이미 확인한 것과 같다 — TEMP DEBUG
LANDMARKS 기준 실제 얼굴 비율이 평균 36.5%(최소 28.9%)로, 세로보다
훨씬 크고 안정적이었다(물리적 화각 정렬 효과).

흥미로운 점: 가운데 크롭 적중률은 가로가 더 낮았는데(32.7% vs 58%),
최종 결과는 더 좋았다. 원인: 가로일 때 `FaceImage`가 90도 회전으로
`480×720`(세로로 긴 모양)이 되는데, 가운데 크롭은 그 720 중 가운데
480만 남기고 위아래를 자른다. 얼굴이 이 축에서 정확히 중앙이 아니면
크롭을 벗어나 fallback이 잦아진다. 하지만 fallback(전체 프레임
재시도)이 있어서, 크롭을 못 맞춰도 전체 프레임 자체에 얼굴이 이미
크게(28~86%) 잡혀 있으니 결국 잘 찾아낸다 — **안전장치가 정확히
의도한 대로 작동한 사례**. 세로로 긴 프레임일 때 크롭 중심을 살짝
위로 옮기는 미세조정도 가능하지만, fallback이 이미 잘 메꿔주고
있어서 우선순위는 낮다고 판단해 보류했다.

**알게 된 것 (핵심 통찰)**
- 작은 얼굴 = 적은 픽셀 = 센서 노이즈에 취약 — 랜드마크 흔들림도 검출
  점수 flicker도 전부 이 하나의 메커니즘에서 나온다(8/13 문서와 11번).
- "화면이 정상으로 보인다"가 "ML 파이프라인이 정상"이라는 보장이 아니다
  — 프리뷰와 ML 경로가 분리된 코드 경로였던 게 이번 세션 최대 발견(4번).
- 폰을 쥐는 방향에 따라 카메라의 실질 화각이 달라져서, 같은 사람·같은
  거리라도 얼굴/프레임 비율이 크게 달라진다(3~4번, 13번에서 재확인).
- 판단이 필요한 적응형 로직(자동 줌, bbox 기반 리파인먼트)은 판단
  근거 자체가 불안정한 바로 그 상황에서 작동하기 어렵다 — 닭과 달걀
  문제(11~12번). 판단이 필요 없는 고정 기하학 개선(가운데 크롭)이
  오히려 이 문제를 원천적으로 피해간다.
- 소프트웨어 크롭과 카메라 레벨 줌은 근본적으로 다르다 — 캡처 단계에서
  이미 버려진 정보는 그 이후 아무리 잘 잘라도 못 되살린다(6번).

  fallback 패턴을 재사용하려다, 실은 실기기에서 단 한 번도 성공한 적
  없었다는 걸 뒤늦게 확인했다(12번, 사용자 질문 덕분에 발견).

- **라이브니스 재활성화**: `_kLivenessEnabled = false`는 임시 디버깅
  플래그다 — 인식 안정성이 이제 충분히 확인됐으니 다시 `true`로 돌리고
  통합 테스트, `face lost` 500ms 유예시간이 여전히 너무 자주 리셋을
  유발하는지 별도 재측정.
- 세로로 긴 프레임(가로 파지)에서 가운데 크롭의 수직 중심을 미세조정할
  가치가 있는지 — 지금은 fallback이 잘 메꿔주고 있어 우선순위 낮음.

## 부록: 바뀐 것들

- `example/lib/main.dart` — `_cameraQuarterTurns()`가 고정 계산 대신
  `_baseQuarterTurns + quarterTurnsForOrientation(liveOrientation)`을 사용.
  `FaceOverlayPainter` 호출부 `quarterTurns: 0`(이중 회전 방지). 자동 줌
  피드백 루프(`_maybeAdjustZoom`) 및 상시 노출 프레이밍 힌트(`_framingHint`)
  추가. 초기 안내 문구를 "가로로 들고" 지시에서 일반 안내로 변경(방향은
  이제 자동 대응). 1차 실기기 검증(log2.txt)에서 발견된 자동 줌 진동을
  잡기 위해 `_minZoom` 1.0 클램프, 쿨다운 900ms, 스텝 0.15, 연속 3프레임
  조건 추가. 2차 실기기 검증(log3.txt)에서 발견된 줌 방향 부호 반전
  버그 수정. 라이브니스 인식-안정성 검증과의 변수 분리를 위해
  `_kLivenessEnabled` 임시 플래그 추가(현재 `false`). 프레임 처리 시간
  진단용 `[Timing]` 로그 추가. 카메라 프리뷰에 항상 표시되는 프레이밍
  가이드 박스(`_guideRegion`) + 안내 문구 추가.
