# AuraFace 유사도가 낮게 나온 하루 — 버그 두 개가 겹쳐 있었던 이야기

**날짜:** 2026-07-24
**증상:** AuraFace를 기본 임베딩 모델로 붙였는데, 분명 본인 얼굴인데 코사인 유사도가
0.14~0.37 사이에서 계속 흔들렸다. 임계값(0.40)조차 못 넘길 때가 더 많았다.
**결론(스포일러):** 서로 완전히 무관한 버그가 **두 개** 겹쳐 있었다. 하나는 모델과
무관한 카메라 회전 문제, 다른 하나는 AuraFace 이 모델 하나만의 정규화 상수 문제.
하나씩 고칠 때마다 "조금 나아졌는데 여전히 이상한" 상태가 반복됐고, 둘 다 고치고
나서야 완전히 정상화됐다(0.81~0.94).

이 글은 그 과정을 가감 없이 남긴 기록이다. 정답으로 가는 지름길은 없었고, 틀린
가설을 몇 개나 거쳐서야 진짜 원인에 닿았다. 이 프로젝트는 [Claude
Code](https://github.com/anthropics/claude-code)와 협업해서 개발했고, 이 디버깅도
마찬가지다 — 그래서 오답들도 그대로 남겨둔다.

## 0. 배경

facekit은 임베딩 모델을 BYOM(Bring Your Own Model) 구조로 갈아끼울 수 있게
설계되어 있다. 기존엔 ArcFace(`buffalo_l`/`w600k_r50`)가 예제 앱의 기본값이었는데,
비상업 연구 라이선스라 release 빌드에 못 넣는 한계가 있었다. 그래서 상업적으로도
재배포 가능한 **AuraFace**(fal.ai, glintr100 기반, Apache 2.0)를 새 기본값으로
붙이기로 했다.

manifest 작성, `adapterForFamily()`에 `'auraface'` 케이스 추가, 라이선스 태그
확인, `tool/fetch_models.sh`로 GitHub Release에서 가중치 받는 스크립트까지 — 여기까지는
평범한 작업이었다. 문제는 실기기에서 등록→인식을 해봤을 때 시작됐다.

## 1. 첫 번째 삽질: "색 순서인가?"

RGB로 시작했는데 유사도가 낮았다. AuraFace README 예제에 `cv2_image[:, :, ::-1]`
(BGR↔RGB 반전) 코드가 있었던 걸 근거로 BGR로 바꿔봤다. 그런데 오히려 더 낮아졌다
(0.31→0.25).

나중에 InsightFace 공식 구현(`model_zoo/arcface_onnx.py`)의 `swapRB=True` 관례를
다시 찾아보니, 그 반전 코드는 사실 "cv2가 기본으로 읽는 BGR을 모델에 넣기 직전에
RGB로 바꿔주는" 코드였다. 즉 애초에 RGB가 맞는 방향이었고, BGR로 바꾼 건 방향을
잘못 짚은 거였다. **채널 순서는 처음부터 범인이 아니었다.**

## 2. 두 번째 삽질: "모델 변환이 깨졌나?"

다음 의심은 `.onnx → .tflite`(fp16) 변환 과정이었다. `onnx2tf`로 직접 변환한
산출물이라 변환 버그 가능성을 배제할 수 없었다. 같은 임의의 입력을 원본 `.onnx`와
변환된 `.tflite`(fp32/fp16) 양쪽에 넣어 코사인 유사도를 비교했다:

```
onnx vs tflite(fp32): cosine ≈ 0.9999999
onnx vs tflite(fp16): cosine ≈ 0.9999988
```

변환은 거의 완벽했다. 입력/출력 텐서 shape(`[1,112,112,3]` → `[1,512]`)도, 원본
ONNX 그래프의 전처리 유무도 확인했다 — 첫 연산이 바로 `Conv`라 그래프 안에 정규화가
내장돼 있지도 않았다. **모델 변환도 무죄.**

## 3. 세 번째 삽질: "raw 임베딩이 이상한가?"

혹시 텐서를 잘못 읽고 있나 싶어 임베딩 벡터 자체의 통계(`min`/`max`/`L2 norm`)를
찍어봤다. `l2Norm`이 10~15대, `min`/`max`가 ±1.3~2.5 정도로 — 완전히 건강한
범위였다. NaN도, 0으로 수렴하는 것도, 포화되는 것도 없었다. **파이프라인 배관도
멀쩡했다.**

## 4. 진짜 문제를 보다 — 정렬된 크롭 이미지를 직접 꺼내기

여기까지 세 가지를 다 지웠는데도 유사도는 낮았다. 그래서 "이론으로 추론하지 말고
실제로 무슨 이미지가 모델에 들어가는지 눈으로 보자"로 방향을 바꿨다. 정렬된
112×112 크롭을 기기 밖으로 꺼내는 데만 세 번 실패했다:

1. **클립보드 + base64**: 37KB 문자열이 채팅에 붙여넣는 과정에서 그냥 잘렸다.
2. **외부 저장소에 파일로 저장 + `adb pull`**: Android 스코프드 스토리지가 앱
   자체의 `Android/data/<pkg>/` 폴더 생성조차 막았다(`Permission denied`) — 이건
   Context API를 거쳐야만 되는 부분이라 순수 `dart:io`로는 우회 불가.
3. **로컬 HTTP 서버 + `adb forward`**: `HttpServer.bind`가
   `SocketException: Operation not permitted (errno=1)`로 실패 — 기기 정책이
   서버 소켓 생성 자체를 막고 있었다.

결국 **base64를 짧게 잘라 여러 줄의 `debugPrint`로 찍고, 터미널 로그를 통째로
복사해서 재조립**하는, 가장 원시적인 방법만 끝까지 통했다. 이렇게 꺼낸 크롭을
PNG로 복원해서 봤더니 — 정상적인 얼굴이 아니라 **얼굴이 위아래로 180도 뒤집혀
있거나, 대각선으로 찌그러진 채** 나오고 있었다.

## 5. 알고 보니 모델 문제가 아니었다 (그런데 바로 알아채진 못했다)

"180도 뒤집힌다"를 보고 처음엔 5점 정렬 계산(Umeyama/SVD)의 부호 계산이 불안정한
게 아닌가 의심했다. 그런데 이 가설을 검증하려다 스스로 실수를 했다 — 서로 다른
세션에서 나온 랜드마크 숫자와 크롭 이미지를 섞어서 잘못 비교한 것이다. 그 실수를
바로잡고, `AffineAligner.align()` 안에 실제 계산된 아핀 행렬을 크롭 덤프와 정확히
짝지어 로그로 남기도록 코드를 고쳤다.

그렇게 얻은 실제 데이터(24개 이상의 호출)를 보니 — **행렬 계산 자체는 완전히
안정적**이었다. 회전각이 매끄럽게 분포하고, 반사(reflection) 부호가 튀는 경우도
없었다. 범인은 정렬 수학이 아니었다.

그럼 왜 뒤집힌 크롭이 나왔을까? 카메라가 주는 **원본 랜드마크 좌표 자체가 이미
회전된 상태**로 들어오고 있었다. 확인을 위해 임시로 (라이선스상 release 빌드에선
막히는) ArcFace `buffalo_l`로 잠깐 바꿔서 같은 카메라 조건으로 테스트해봤는데 —
**정확히 같은 패턴**이 나왔다. 즉 이건 AuraFace만의 문제가 아니라, **모델과 무관한,
detect/align 파이프라인 공통의 문제**였다.

원인을 뜯어보니 단순했다: `_toFaceImage()`(YUV→RGB 변환)가 카메라 센서가 주는
원본 버퍼를 그대로 썼고, `sensorOrientation` 기반 회전 보정이 **애초에 코드에
없었다**. 이 결함은 프로젝트 시작부터 있었는데, 예전엔 후면 카메라 + 가로로 들고
쓰는 조건에서 우연히 드러나지 않았고, 최근 "화면 보면서 라이브니스 확인하려고"
전면 카메라를 기본값으로 바꾸면서(세로로 들고 셀카 찍듯 쓰게 되면서) 처음으로
문제가 됐다.

**수정:** `rotateFaceImage()`(순수 회전 함수)를 추가하고, `_toFaceImage()`에서
`CameraDescription.sensorOrientation`과 렌즈 방향(전/후면)을 기반으로 회전량을
계산해 프레임을 detect 이전에 바로잡도록 했다.

**결과:** ArcFace `buffalo_l`로 재확인 — 유사도가 0.14~0.37에서 **0.43~0.69**로
뛰었다. 확실한 진전이었다.

## 6. 그런데 AuraFace는 여전히 낮았다

회전 버그를 고친 그 상태로 AuraFace를 다시 테스트했는데 — 여전히 0.06~0.40대였다.
**즉 회전 버그는 실재했고 고쳐졌지만, AuraFace에는 완전히 별개의 두 번째 문제가
남아있었다.**

이번엔 정렬 크롭이 정상적으로(똑바로 선 얼굴로) 나오는 걸 먼저 확인했다. 그래서
그 실제 크롭 두 장(같은 사람)을 오프라인 검증 하네스에 넣고, 정규화 조합을
체계적으로 다시 훑었다:

```
(pixel-127.5)/127.5, RGB   → self-similarity 0.148
(pixel-127.5)/127.5, BGR   → self-similarity 0.169
0~1 정규화, RGB             → self-similarity 0.169
0~1 정규화, BGR             → self-similarity 0.204
정규화 없음(raw 0~255), RGB  → self-similarity 0.9325  ← ★
정규화 없음(raw 0~255), BGR  → self-similarity 0.9280
```

**표준 ArcFace 관례인 `(pixel-127.5)/127.5`가 아니라, 정규화 없이 원본 0~255
픽셀을 그대로 넣어야 하는 모델**이었다. `glintr100.onnx`를 fp16으로 변환하는
과정에서 정규화가 그래프에 흡수됐거나, fal.ai의 이 배포판이 애초에 다른 컨벤션을
쓰는 것으로 보인다.

**수정:** `manifest.json`의 `normalize`를 `mean=[0,0,0], std=[1,1,1]`로 변경.

**결과:** 실기기 재테스트 — 유사도 **0.81~0.94**, 15번 시도 전부 `accepted=true`.

## 7. 정리 — 두 버그의 인과관계

```
카메라 회전 보정 없음 (모델 무관, 원래부터 있던 결함)
   └→ 전면 카메라 기본값 전환으로 실사용 조건에서 처음 노출
   └→ ArcFace로 재확인: 0.14-0.37 → 0.43-0.69 (수정 후)

AuraFace 전용 정규화 오류 (이 모델 변환본만의 문제)
   └→ 회전 버그를 고친 뒤에도 AuraFace만 여전히 0.06-0.40
   └→ 실제 크롭으로 재검증: raw(무정규화) 0.93 vs 정규화 0.15-0.20

둘 다 수정 → 0.81-0.94, 정상화
```

두 버그가 동시에 존재했기 때문에, 하나씩 고칠 때마다 "부분적으로만 나아지고
여전히 이상한" 결과가 나왔다. 만약 첫 번째(회전) 수정 후 바로 "됐다"고 판단했으면
두 번째 문제를 영영 못 찾았을 것이고, 반대로 회전 문제를 먼저 못 찾았으면 정규화를
고쳐도 유사도가 이상하게 낮게 남아 "여전히 뭔가 이상하다"는 결론에 머물렀을
것이다.

## 8. 배운 것

- **이론적 추론(색 순서, 변환 신뢰성)으로 배제한 것들은 진짜로 배제됐다** — 다만
  그것만으론 답에 못 닿았다. 결정적 전환점은 항상 "실제로 무슨 데이터가 오가는지
  직접 꺼내서 눈으로 보는" 순간이었다(정렬 크롭 이미지, 실제 아핀 행렬, 실제
  랜드마크 좌표).
- **기기에서 데이터를 꺼내는 것 자체가 별도의 난관이었다.** 클립보드, 외부 저장소,
  로컬 서버가 각각 다른 이유로 막혔고, 결국 가장 투박한 방법(로그를 텍스트로
  쪼개서 찍고 다시 합치기)만 끝까지 살아남았다. 화려한 방법이 항상 이기는 건
  아니다.
- **두 원인이 겹쳐 있을 가능성을 열어둬야 한다.** 하나를 고쳤는데 "나아졌지만
  아직 이상하다"는 신호가 나오면, 그건 그 수정이 틀렸다는 뜻이 아니라 다른 문제가
  더 있다는 뜻일 수 있다.
- **같은 대조군(arcface_buffalo_l)을 계속 유지한 게 결정적이었다.** 회전 버그가
  모델과 무관하다는 걸 증명한 것도, 정규화 문제가 AuraFace 고유의 문제라는 걸
  증명한 것도, 전부 "다른 모델로 같은 조건에서 재현되는지"를 확인했기 때문에
  가능했다.

## 부록: 남겨둔 디버그 도구

이 조사 과정에서 만든 진단 로그(정렬 크롭 base64 덤프, 랜드마크 로그, 아핀 행렬
로그, raw 임베딩 통계)는 코드에서 지우지 않고 `lib/src/core/debug_flags.dart`의
`kFacekitVerboseDebug` 플래그 뒤에 남겨뒀다. 평소엔 꺼져 있어 빌드에 전혀 안
들어가고, 필요할 때 아래처럼 한 번만 켜면 된다:

```bash
flutter run --dart-define=FACEKIT_VERBOSE_DEBUG=true
```
